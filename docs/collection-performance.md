# 采集性能与正确性

## 已实现的优化

1. 文件解析缓存按 mtime、ctime、文件大小和依赖文件指纹复用结果。未变化时不序列化、不重写缓存；变化时先写临时文件再原子替换，失败后可重试，缓存故障不阻止采集。
2. 完整归一化结果按日期计算签名，保存在 `collection_checkpoints` 中，设备与来源分别隔离。无变化时跳过用量表读取和写入；变化时读取对应日期的日汇总、事件，以及兼容工作区统计。其他日期的项目活动通过数据库聚合保留，不加载其全部事件。
3. `GET /api/collect/status?wait=1` 在运行期间最多等待 25 秒，结束或失败时立即响应。断开连接会取消订阅；超时返回当前状态，客户端继续等待。普通状态接口仍立即返回，鉴权规则不变，旧服务忽略参数时客户端有退避保护。

采集仍记录每个来源的运行状态。输出中的 `unchanged` 表示归一化输入未变化；`reconciled_dates=N` 表示本次核对了 N 个变化日期，而不是仅保留了 N 天历史。

## 可靠性边界

- 日期签名包含事件身份、日期、模型、项目、各项 token 和费用元数据，不能只比较总 token。补入旧记录、改动元数据、事件跨日期移动都会触发核对。
- 核对和写入在同一事务中完成，费用保留策略与完整核对相同。签名只有在数据成功提交后才生效；解析缓存先更新也不会使失败的数据库写入被跳过。
- SQLite 使用写事务；PostgreSQL/MySQL 使用每个设备/来源固定的进度行锁。公共写入方法、导入、迁移和恢复会在同一事务使该来源签名失效。失效保留进度行，以便首次采集也能与并发导入互斥。
- 无签名、格式不兼容、签名损坏或一次变化超过 180 个日期时使用完整核对。修改核对语义时应提升签名版本。`--dry-run` 和 `--full` 预览始终走完整核对。
- 日志删除或轮转不会自动删除已入库历史。清理旧记录仍需显式的全量替换和备份流程。
- 签名只是可重建的优化状态，不能用于同步确认。直接在应用外修改数据库时，需使对应进度失效后再采集；不要把进度表从另一份数据库单独复制过来。

当前仍会发现文件、加载解析缓存、归一化完整的采集输出，并计算日期签名。没有实现字节偏移续读，也没有改变同步协议。页面查询的后续优化见[大范围查询与按需明细](query-performance.md)。Codex 的模型上下文、累计用量，以及跨文件去重必须在进一步增量化时一起处理。

## 基准方法与结果

2026-09-26，在同一台 macOS 机器上与 `9a58c22` 比较。使用独立数据库、独立解析缓存；冷启动和签名建立不计入下面的热缓存结果。每个场景交替执行两个版本各 5 次，取进程完整运行耗时的中位数，不包含页面刷新。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| Codex 单来源，无变化 | 521 ms | 321 ms |
| Codex 单来源，追加日志 | 523 ms | 361 ms |
| Codex 单来源，补入历史记录 | 538 ms | 362 ms |
| 全来源，无变化 | 1,157 ms | 742 ms |

Codex 三种场景使用 446 个日志文件的固定副本，并追加受控测试记录；每轮三张用量表逐行比对一致（排除运行时间戳与锁定时间戳）。全来源测试读取本机日志、写入数据库副本，最终 927 个日汇总、80,934 个事件、1,186 个兼容工作区统计在两个版本间一致；字段核对仅有浮点费用约 `7.1e-15 USD` 的差异，低于 `1e-9 USD` 的金额比对容差，其他业务字段一致。

这些数据是本机样本，不代表所有设备或远程数据库的耗时。首次运行仍需建立签名，大范围日志变化仍会完整核对。页面完成通知移除原来的固定 1.5 秒轮询间隔，页面查询及渲染耗时需单独观察。

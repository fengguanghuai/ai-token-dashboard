# 采集性能与正确性

当前任务状态与优先顺序统一维护在[项目状态](project-status.md)；本文保留实现边界和测量证据。

## 已实现的优化

1. 文件解析缓存按 mtime、ctime、文件大小和依赖文件指纹复用结果。未变化时不序列化、不重写缓存；变化时先写临时文件再原子替换，失败后可重试，缓存故障不阻止采集。
2. 完整归一化结果按日期计算签名，保存在 `collection_checkpoints` 中，设备与来源分别隔离。无变化时跳过用量表读取和写入；变化时读取对应日期的日汇总、事件，以及兼容工作区统计。其他日期的项目活动通过数据库聚合保留，不加载其全部事件。
3. `GET /api/collect/status?wait=1` 在运行期间最多等待 25 秒，结束或失败时立即响应。断开连接会取消订阅；超时返回当前状态，客户端继续等待。普通状态接口仍立即返回，鉴权规则不变，旧服务忽略参数时客户端有退避保护。

采集仍记录每个来源的运行状态。输出中的 `unchanged` 表示归一化输入未变化；`reconciled_dates=N` 表示本次核对了 N 个变化日期，而不是仅保留了 N 天历史。

## 可靠性边界

- 日期签名包含事件身份、日期、模型、项目、各项 token 和费用元数据，不能只比较总 token。补入旧记录、改动元数据、事件跨日期移动都会触发核对。
- 核对和写入在同一事务中完成，费用保留策略与完整核对相同。签名只有在数据成功提交后才生效；解析缓存先更新也不会使失败的数据库写入被跳过。
- SQLite 使用写事务；PostgreSQL/MySQL 使用每个设备/来源固定的进度行锁。公共写入方法、导入、迁移和恢复会在同一事务使该来源签名失效。失效保留进度行，以便首次采集也能与并发导入互斥。
- 无签名、格式不兼容、签名损坏或一次变化超过 180 个日期时使用完整核对。修改核对语义时应提升签名版本。`--dry-run` 和 `--full` 预览始终走完整核对。
- 日志删除或轮转不会自动删除已入库历史。清理旧记录仍需显式的全量替换和备份流程。
- 签名只是可重建的优化状态，不能用于同步确认。直接在应用外修改数据库时，需使对应进度失效后再采集；不要把进度表从另一份数据库单独复制过来。

当前仍会发现文件、加载解析缓存、归一化完整的采集输出，并计算日期签名。Codex 默认经过完整前缀校验后续解析，仍读取整个变化文件；另有下述可选的只追加字节续读模式。同步已改为事务变更记录，沿用现有 HTTP 上传协议。页面查询的后续优化见[大范围查询与按需明细](query-performance.md)。Codex 的模型上下文、累计用量，以及跨文件去重必须在进一步增量化时一起处理。

## 基准方法与结果

2026-09-26，在同一台 macOS 机器上与 `9a58c22` 比较。使用独立数据库、独立解析缓存；冷启动和签名建立不计入下面的热缓存结果。每个场景交替执行两个版本各 5 次，取进程完整运行耗时的中位数，不包含页面刷新。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| Codex 单来源，无变化 | 521 ms | 321 ms |
| Codex 单来源，追加日志 | 523 ms | 361 ms |
| Codex 单来源，补入历史记录 | 538 ms | 362 ms |
| 全来源，无变化 | 1,157 ms | 742 ms |

Codex 三种场景使用 446 个日志文件的固定副本，并追加受控测试记录；每轮三张用量表逐行比对一致（排除运行时间戳与锁定时间戳）。全来源测试读取本机日志、写入数据库副本，最终 927 个日汇总、80,934 个事件、1,186 个兼容工作区统计在两个版本间一致；字段核对仅有浮点费用约 `7.1e-15 USD` 的差异，低于 `1e-9 USD` 的金额比对容差，其他业务字段一致。

这些数据是本机样本，不代表所有设备或远程数据库的耗时。首次运行仍需建立签名，大范围日志变化仍会完整核对。页面完成通知移除原来的固定 1.5 秒轮询间隔，页面查询及渲染耗时需单独观察。

## Codex 解析续接

Codex 解析缓存保存已完成行的字节位置、SHA-256、原始事件和解析状态（模型、工作区、累计用量、会话身份、turn 与 fork 重放状态）。文件变化后，校验已消费前缀全部字节，匹配时只解析新行；旧内容被修改、文件截断或缓存版本变化时完整解析。不能用头尾抽样代替完整校验，否则中间改写后追加会漏算。

末行没有换行时，仍按原解析器语义展示可解析事件，但不提交其解析状态；下一次重新解析末行，避免半行 JSON、UTF-8 字符或补换行造成重复。解析状态不包含费用，数据库原有费用保留策略不变。`PARSE_CACHE=0` 可绕过缓存。

2026-09-26 的合成测试：63.76 MB Codex 日志追加 138 字节，交替执行完整解析与续接各 5 次，中位数分别为 56 ms 和 46 ms（约减少 18%）。这仅是当时单文件解析耗时，不是整次采集耗时，也不代表真实日志的普遍收益。默认模式仍包含完整文件读取和 SHA-256 校验，缓存事件仍需归一化。

## Codex 可选字节续读

默认不改变可靠性边界。只有能保证 Codex 日志旧内容不被原地改写时，才在采集进程设置 `CODEX_LOG_APPEND_ONLY=1`，并保持 `PARSE_CACHE` 开启。也可在本地 `.env` 配置；本轮没有替用户开启。切换该选项会更新缓存版本、重建完整基线，关闭后恢复默认全前缀校验。其他采集器不受影响。

可选模式保存文件身份、观察到的长度、最后完整行偏移、解析状态及检查点校验和。正常追加只从完整行偏移读取到本次打开时的文件长度；末尾半行会重读，后续追加留给下一次采集。文件替换、观察到的缩短、同长度但元数据变化、检查点损坏或版本改变时重新读取并解析。读取期间观察到截断或改写时本次采集失败，下一次重新核对，不保存混合检查点。

这些检查不能识别“改写历史中部后继续增长”，也不能识别两次采集之间截断再增长到原长度以上的所有情况；这正是显式只追加约束的用途。检查点校验和防意外损坏，不是防恶意篡改。不能把此选项作为任何日志都安全的默认加速开关，也不因此把原始通用 READ-01 标为全部完成。

2026-10-04，在同机合成 64 MiB 日志上追加 157 字节，两种模式各启动 3 个新进程读取持久检查点。默认模式实际读取 67,109,262 字节，可选模式读取 157 字节；两者均只向解析器传入 157 字节，最终事件逐项一致。文件处理耗时中位数约 59.8 ms / 8.0 ms，其中解析约 7.8 ms / 7.4 ms；进程峰值 RSS 中位数约 116.5 / 51.4 MiB（包含 Node 运行时）。此样本只有少量用量事件，不代表大事件缓存的整体收益，也不是整次采集基准。可运行 `node --test test/parse-continuation.test.mjs test/parse-cache.test.mjs` 验证读取字节数、重启及回退语义。
